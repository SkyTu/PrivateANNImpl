# 1M / C=500 / u=15 / B=100 / k=10 实测报告

来源：已保存的单次运行，未重新测试。原始数据为 [CSV](../../logs/cluster_bucket_once.csv)、[日志](../../logs/cluster_bucket_once.log)、[进程计时](../../logs/cluster_bucket_once.time)。这是连续显存预分配优化之前的实现。

## 配置

- NVIDIA L40S-48Q，单 GPU；TFHE 同层调度使用 4 个 CPU 工作线程。
- 1,000,000 条记录，128 维，每个元素 uint8。公开合成数据，500 个均衡簇，每簇 2,000 条。
- 500 个质心距离选最小的 15 个，对应 30,000 个候选；候选再分为 **100 个桶，每桶 300 条**。
- 每桶取最小距离及关联 ID，再从 100 个优胜者中选最终 Top-10。
- 距离完整 23 位、不截断；距离与 ID 分别存 FheUint32，仅比较距离，并列可任选。
- BFV N=4096，明文模数 8,380,417，百万条距离分 245 批。

## 正确性和范围

**PASS，退出码 0。** 全部 1M BFV 距离、500 个转换结果、质心 Top-15、100 个桶优胜者及最终 Top-10 均通过独立明文参考检查，包括距离和 ID 的关联。相对于合成的 30,000 候选集合，distance recall@10 为 0.9；每桶仅保留一个优胜者使一个候选近邻被同桶更近的记录淘汰。这不是全量 1M 数据的召回率。

**这是组件实验，不是完整的秘密查询耗时。** 当时尚未实现 TFHE 选簇结果控制的 BFV oblivious gather，也未运行这 30,000 个候选距离的 BFV→TFHE 转换。候选由公开合成数据的明文参考预先准备，再由客户端直接加密成 TFHE；没有把解密后的簇选择结果用于服务器路由。上述两个缺失阶段不包含在 43 分 2 秒内。CSV 明确记录 `full_pipeline_executed=0`、`oblivious_bfv_gather_implemented=0`、`candidate_conversion_executed=0`。

本次桶内操作是 **最小值**，与随后用于排查并行及连续显存的“300 取最大值”实验不同。尚未用新分配器重新测量这套大规模组件。
